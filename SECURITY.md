# Безопасность локального фотоархива

Проект предназначен для локальной учебной установки. Контейнерный веб-порт привязан к 127.0.0.1; PostgreSQL не публикует порт. Все фотографии и названия доступны для чтения посетителям этой установки, а создание, изменение и удаление требуют действующей сессии. Это общий каталог, персональных закрытых альбомов нет.

Автономная Windows-версия также слушает только127.0.0.1 и запускается обычной учетной записью. Не создает службы, не меняет системный PATH или реестр, не скачивает компоненты при запуске. Ее секреты и рабочие данные находятся в `data/`, отдельно от Docker-томов. Нативные static/media маршруты доступны только в opt-in режиме DJANGO_PORTABLE и проверяют разрешенные типы и принадлежность пути, включая NTFS junction.

## Реализованные меры

- Пароли БД/администратора/pgAdmin и секрет Django генерируются криптографически при первом запуске; универсального рабочего пароля нет. `.env.docker` не включается в Git и Docker build context.
- Пароль администратора хранится в БД в виде Django password hash. Повторный запуск не меняет пароль существующего аккаунта и не восстанавливает удаленную демофотографию.
- Session authentication, CSRF на входе/выходе и операциях записи, точные allowed hosts и доверенные origins. DEBUG выключен по умолчанию; отсутствие секрета останавливает запуск.
- Сервер проверяет тип содержимого, размер загрузки до 10 МиБ и число пикселей до 25 миллионов. Поддерживаются статические JPEG/PNG/WebP; анимация не принимается. Проверка браузера `accept` служит только подсказкой.
- Оригинал и миниатюра сохраняются с управляемыми хранилищем именами; старые файлы удаляются после подтверждения транзакции. Невалидный новый файл не должен разрушать прежнее изображение.
- Nginx ограничивает размер HTTP-запроса, скорость обращений к авторизации и добавляет защитные заголовки. Медиа выдаются статически с отдельной политикой CSP.
- В нативной версии Waitress ограничивает тело запроса, Django выдает явные безопасные файловые маршруты и CSP/nosniff; вход API и Django Admin используют общий ограничитель попыток. Контроль дочерних процессов выполняется собственными handles/Job Object и бинарной проверкой postmaster.pid; случайный PID из файла не завершается.
- Зависимости проверяются pip-audit/pnpm audit, Python-код — Bandit; CI выполняет регрессионные и интеграционные тесты.

## Границы защиты

Локальный HTTP использует cookies без Secure, чтобы работать без настройки сертификата. Если сервис переносится на внешний сервер, установите HTTPS, `DJANGO_SECURE_COOKIES=1`, точные `DJANGO_ALLOWED_HOSTS` и `DJANGO_CSRF_TRUSTED_ORIGINS`, настройте TLS reverse proxy и резервные копии. Привязка к loopback сама по себе не является авторизацией.

Файловая система и PostgreSQL не образуют общей аппаратной транзакции. Внезапное завершение процесса/потеря питания могут оставить лишние файлы; храните согласованные резервные копии БД и media. Ограничение одного файла не задает общую квоту диска. Для публичного многопользовательского хостинга дополнительно нужны квоты, права владельцев, мониторинг, политика хранения и отдельный origin для недоверенных медиа.

Не публикуйте `.env.docker`, резервные копии БД и пользовательские фотографии. Если секрет стал доступен посторонним, замените его локально и сбросьте соответствующий пароль через штатные средства Django/PostgreSQL. Изменение строки пароля в env не меняет пароль уже созданной БД или существующего администратора.

Результаты проверки относятся к версии кода и дате, указанным в `docs/review.md`. Отсутствие известных уязвимостей по базе advisories не является доказательством отсутствия всех ошибок.
